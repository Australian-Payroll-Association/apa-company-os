Managing and testing the stack

How the setup skill and prompt are owned, versioned, released, and proven: one product repo, one release train, and two testing channels feeding one improvement loop.

Architecture

One product repo, everything else consumes

All content lives in the template repo. The plugin carries no skills, the workshop page owns no prompt text, and machines pull updates through one path. The fork that caused this project is structurally impossible.

Edits happen in one place; releases move one branch; three consumers read it. No second maintained copy exists anywhere.
Management process

The release train

One version number for the whole system, defined meanings for each bump, and a pipeline where the printed handout URL never changes but its content moves only deliberately.

BumpMeansTesting required
MajorThe flow changed in a way that invalidates printed handouts or requires re-running setupAll nine runs, both channels

Ownership

Who does what

Operator
Owns the experience

Reviews every change to setup-skills and prompts (CODEOWNERS). Settles open decisions. Cuts releases. Runs the pre-retreat dress rehearsal.

Engineers
Own the pieces

PR all changes to main; never hand-edit a client machine without filing the fix the same day. Onboard with the real prompt, verbatim: their setups are the field tests.

CI
Owns the contract

Contract test, gate lint, reference resolution, stable pinning, secret shapes, and the plugin-repo guard that fails if a skills directory ever reappears.

Never hand-edit agents, skills, or scaffold files on a client machine. Changes go to the canonical repo by PR, get released, and reach machines via the patch skill.
Testing process

Three channels, one evidence pool

Cheapest first: CI statics catch contract drift in seconds, the onboarding fleet tests reality for free, and a small crash rig does what you can't ask of a real engineer.

Stage F of the skill files the report itself: engineers' runs become issues on the repo automatically; outside attendees get a local SETUP-REPORT.md.
The improvement loop

Install bugs become the next version

The DOXA engineers onboarding now are the first fleet: v2 can have real field reports before Sydney.
