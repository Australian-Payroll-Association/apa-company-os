Human Tokens in the Client Portal

Folding the Human Token Tracker into Edge8: one login, one platform, and every client seeing what they bought, what we planned, and what we actually delivered.

01 · Why

Two problems, one root cause

A client (Australian Payroll Association) could not log into the Human Token Tracker. The reason is structural: the tracker is a separate app with its own Supabase login, a second account edge8 clients do not have. That is the symptom.

The goal underneath it: clients should see their human tokens inside the Edge8 client portal, not in a separate product with a separate password. So we resolve both at once: retire the second login, and surface the numbers where clients already are.

One line: the Human Token Tracker stops being a separate product and becomes a feature of Edge8: same login, same portal, per AI Program.

Because the stacks are identical and the tracker's data is small (low thousands of rows), this is a code-and-data merge, not a re-platform. The effort is in three places: schema namespacing, reconciling identity, and re-homing the telemetry pipeline.

03 · The word "project" means two things

Split it before anything else

This naming clash is the trap. Keep the two meanings apart:

  • The tracker's projects table is really one GitHub repo (it enforces one repo per row).
  • What we call a Project is a delivery engagement, and we already have a name for it: an AI Program.

An AI Program is the unit. Australian Payroll Association runs two: Fair Pay and PayrollIQ. They are completely separate, each with its own repo, its own board, its own roadmap. So one client can hold several AI Programs.

04 · The model

Client, then AI Program, then one clean spine

A client is flagged as an AI Program client. Each of their AI Programs owns exactly one repo, one workboard, and one roadmap, and everything the tracker measures hangs off that repo.

COMPANY · Australian Payroll Association flagged is_ai_program → tracker on, needs ≥1 repo
AI PROGRAM · Fair Pay
1 repo 1 workboard 1 roadmap tracking: tokens + hours + PRs Group D: goals, ROI, summaries
AI PROGRAM · PayrollIQ
1 repo 1 workboard 1 roadmap tracking: tokens + hours + PRs Group D: goals, ROI, summaries

The spine is 1 repo = 1 AI Program = 1 board = 1 roadmap. That is the decision that makes everything else fall into place, because in the tracker's schema every measurement table and every Group D table already points at the repo. Anchor the repo to the AI Program and the goals, ROI, and summaries come along for free and roll up the same way the tokens do.

What "the AI Program layer" is, concretely

Edge8 already has an ai_programs table (many per company). It becomes the Project layer. The roadmap (client_roadmap_overview + client_backlog_items) and the workboard (boards) move from being keyed to the company to being keyed to the AI Program. The tracker's repo, ROI config, and measurements attach to the same AI Program.

Scope: the tracker is about code. A repo is code development. Retreats and consulting are separate work and are out of scope here; design work is legacy and ignored. Human-token tracking follows the code.

05 · What the client sees

Three numbers per AI Program, fully transparent

Human tokens are the same unit on both sides: one token is one hour of skilled human work. Purchased tokens are credits; delivered hours are debits. Netted together, a client sees:

Bought

Credits they paid for, from Stripe and invoice. Both sources kept.

Planned

Our estimate: the roadmap range, refined into workboard card estimates.

Delivered

Actual measured hours, plus the AI leverage ratio, from telemetry.

Clients see planned against delivered, in full. When we are efficient it shows; when a job overran it shows too. Transparency is the point. Group D (goals, ROI, leverage, summaries) appears as a rolled-up engagement view with an optional per-repo drill-down.

Everything moves into a dedicated htt schema inside Edge8's Supabase project, not public. That sidesteps every table-name collision (the tracker has generic names like clients, projects, notifications that would clash).

07 · GitHub identity

Three entities, three GitHub identities

Attribution lives or dies on GitHub identity, and it sits at all three levels of the hierarchy. Each one answers a different question: which client owns the code, which AI Program a repo belongs to, and which person did the work.

LevelStored asWhy
Company → org New company_github_orgs (company, org_login), 1..n per client The GitHub App install target (needed to read private repos), repo grouping and discovery
AI Program → repo On ai_programs: repo_url, github_repo (canonical org/name, the join key), github_repo_id (numeric, rename-proof) One repo per AI Program; telemetry and PR sync key on the canonical name
Person → account people.github_login (1:1) + new person_git_emails (email, source), 1..n PRs attribute by login; commits and hours attribute by email, and one person commits under several

Collected on intake

The onboarding survey gains two optional questions: GitHub username (mapped to people.github_login, normalized) and git commit email (upserted into person_git_emails as the primary; a small handler is needed because that is a child table, not a single profile field). Both optional: only people who commit fill them in. Further commit emails are discovered automatically during ingestion.

At ingest it resolves cleanly: repo → AI Program → company gives the scope; a PR's author login maps to a person via github_login; a commit email maps via person_git_emails; bot and service-account commits are excluded. Uniqueness rules keep it honest: one GitHub account per person, one commit email per person, one repo per AI Program.

08 · How we get there

Phased, client-visible win first

Phase 0

Schema

Add is_ai_program to companies. Extend ai_programs into the Project layer. Create the htt repo, tracking, and Group D tables with FKs to companies, people, and AI Program.

Phase 1

Re-key roadmap and board to the AI Program

Give every existing client a default AI Program and move their roadmap and board onto it. This touches live portal features, so it needs care and QA.

Phase 2

Bring the tracker data in

Copy the tracker rows into htt, re-pointing client to company, contributor to person, repo to AI Program.

Phase 3

Surface it in the portal

The portal shows Bought / Planned / Delivered plus the leverage ratio per AI Program, rolled up with per-repo drill-down. Reads go through the existing portal auth and company scope. This is the visible client win.

Phase 4

Re-home ingestion, retire the second login

Redeploy the telemetry edge functions to Edge8's Supabase, re-create the CI secrets, repoint the hardcoded URLs, migrate the tracker's users into Edge8 auth, and delete the standalone login. The riskier cutover, done last.

Phases 0 to 3 give clients the visible result. Phase 4 is the auth and pipeline cutover and comes last so the blast radius stays small.

09 · Still to work out

Technical reconciliation, not open decisions

  • Credits unification. One balance view over Stripe purchases and invoice/manual allocations: dedupe, currency, and whether the balance sits at the company or the AI Program.
  • Non-code work. Retreats and consulting are not repos and are not measured here. The client view should be explicit that tracked delivery is code, so the numbers are not mistaken for total effort.

GitHub identity (how people and repos attribute) is resolved: see section 07.

10 · Risks

  • Table-name collisions, mitigated by the dedicated htt schema.
  • Two auth and RLS philosophies, plus migrating users across Supabase projects (Phase 4).
  • Re-keying live roadmap and board features from company to AI Program (Phase 1).
  • Folding a telemetry pipeline into the production Edge8 deploy widens the blast radius.

Strategic note: full absorption means the Human Token Tracker can no longer run as a standalone product with its own customers. If that path still matters, we stop at shared login instead of a full merge. The plan above assumes it becomes a feature of Edge8.
