CLAUDE.md cleanup: diagnose and fix your own machine

26 Aug 2026 · based on the cleanup of all 13 active projects on Dave's machine

We audited every project in code-projects and found the same rot patterns repeating. This brief covers what we found, then gives you two prompts to run against your own machine. You don't run anything in the terminal yourself: point Claude at your projects folder and paste the prompt.

1. The problems we found

  • Stub files with no map. Four projects had a 26-line CLAUDE.md that was nothing but an agent-delegation table. An agent opening the repo learned who to delegate to, but nothing about the stack, the database, or how to ship.
  • Essay files that had rotted. One project had 325 lines including a 90-line folder tree that was badly wrong (it listed 7 pages; the site has about 90 routes). Long files rot fastest because nobody re-reads them.
  • Confidently wrong facts. One file said "Pages Router" for an App Router app. One named the wrong GitHub repo. Two documented a retired database as if it were live. Delegation blocks referenced persona files that do not exist in that repo.
  • Missing files. Two active projects had no CLAUDE.md at all, so every session started from zero.
  • Invented-system risk. Several projects have no written design system. When the file does not say so explicitly, agents invent hexes and components on the fly.
  • Stale worktrees eating disk. Seven orphaned worktree folders (about 5.5 GB) had been moved aside but were still registered in git. Stale copies under .claude/worktrees/ also pollute search results in most repos.
  • Root clutter that misleads. Stale root .env.local files (one cost a whole session), boilerplate READMEs, committed build artifacts.

2. Diagnose your machine

Open Claude Code in your projects folder (cd ~/code-projects && claude, or open the folder in the desktop app). Use Opus or better. Paste this:

Diagnosis prompt

Audit every project in this folder for CLAUDE.md health. Read only, change nothing. For each project directory, report one line with a verdict (MISSING, STUB, ROTTED, or HEALTHY) and why: 1. Does a CLAUDE.md exist? If not, mark MISSING. 2. Does it OPEN with a map that answers all five: where the design system or style guide lives (or an explicit "none exists"), where tokens live (CSS vars, theme file, tailwind config), whether there is a component reference to copy from, what the stack is and where data comes from, and how the project ships (branch, PR, gates, deploy)? A file that is mostly an agent-delegation table with no map is a STUB. 3. Verify the file against the repo, not against itself: check the router type and framework against package.json and the app directory, the repo name against git remote -v, the database against what the code connects to, and confirm every file path the file mentions actually exists. Wrong facts or dead references mean ROTTED. 4. Flag length: under 30 lines is probably a stub, over 100 is probably an essay that will rot. 30 to 60 is the target. 5. Also check git hygiene: run git worktree list in each repo and flag anything marked prunable, plus stale copies under .claude/worktrees/ and any stale root .env.local where the real one lives in a subfolder. Finish with a summary table and the list of projects that need the cleanup prompt.

3. Clean up your machine

For each project the diagnosis flagged, run this in the same session (or a fresh one in the projects folder):

Cleanup prompt

Rewrite the CLAUDE.md files flagged in the audit as map-first files. Rules: 1. Archive first: copy the existing CLAUDE.md to docs/archive/CLAUDE-md-pre-rewrite-<today>.md inside the same repo before changing anything. Nothing is lost. 2. Derive everything from the repo, not from memory: read package.json, the globals or theme CSS, the route tree, the README, and the last 15 git log entries before writing a word. 3. Open with a map answering the five questions: design system location, token location, component reference, stack and data source, ship flow. Concrete file paths, not descriptions. 4. Never invent a design system, token set, or convention. If none exists, write "no design system exists; globals.css is the truth" instead. 5. After the map, keep only the load-bearing rules that have actually burned a session (wrong-database gotchas, auth boundaries, deploy rails). Point at docs for everything else. Target 30 to 60 lines. 6. Scope every rule: no unscoped "never". Say where each rule applies. 7. Preserve any managed AGENT-DELEGATION block byte-for-byte between its BEGIN and END markers, below the map. 8. Prefer pointers over lists that rot: "enumerate domains with ls src/features" beats a hardcoded list. 9. For stale worktrees: run git worktree prune, but before deleting any orphaned folder, check it for uncommitted work with git status and keep anything that has real changes for me to review. 10. Leave everything uncommitted in the working tree and give me a one-line report per project. Do not commit, push, or open PRs unless I say so.
The contract going forward: the tree wins over any doc. When you notice a CLAUDE.md and the code disagree, fix the file in the same PR. edge8-web/CLAUDE.md is the reference copy of the standard.
