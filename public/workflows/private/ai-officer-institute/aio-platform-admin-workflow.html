Two ways in

Edge8 staff have two separate credentials

There isn't one "admin login". Two independent credential systems occupy adjacent space by design, and which one you hold decides what you can reach.

Credential one

System admin

user_role.role = admin / super_admin · the legacy path
  • A normal session plus an admin/super_admin role row.
  • Re-checked from the database on every request — a tampered cookie gets nowhere.
  • Opens the back-office routers and cross-company reads.
  • Held by very few accounts — three, as of 1 Aug 2026.

How Edge8 devs and staff reach the back office today.

Credential two

Platform operator

the /platform console · a separate allowlist
  • Signs in through the console's own OTP login — a distinct platform_session.
  • Gated purely by an operator allowlist; it never consults user_role.
  • Phase-1 scope: cross-company reads plus the support inbox.
  • Every change it makes writes an audit-log row.

Turned off in production today — FEATURE_PLATFORM_CONSOLE.

One control, two keys

Creating a company accepts either credential — a system admin, or an elevated console operator. It's the one place the two systems meet; everything else stays on its own side of the line.

Company onboarding

Live
router/aio/admin/companies.py · POST /admin/companies

One call stands a whole tenant up. In sequence it:

  1. Creates the company.
  2. Opens an active contract with a generated join code.
  3. Sets the seat cap from the chosen plan.
  4. Seats the client manager (seat #1) and emails them the join link.

The Platform Console

Flag-gated
router/aio/admin/platform.py · FEATURE_PLATFORM_CONSOLE — default OFF

The whole /platform surface for console operators. Phase 1 is reads plus the support inbox; every mutation is audited. It carries:

  • Native login — request an OTP to an allowlisted email, verify, get a console session.
  • Cross-company management — list → company detail (profile, contracts, seats, members) → edit profile (audited, emails every manager) → resend any seat's invite, for any company.
  • Student-progress roster — per-mission status and rollups across all companies.
  • Support triage — list → detail → assign (emails the assignee) → message / update → resolve (emails the requester).
  • Bug reports — list and detail.
  • Staff directory — the picker for assignments.

Destructive student remediation

Flag-gated
router/aio/admin/remediation.py · ADMIN_REMEDIATION_V1 — default OFF

The irreversible tools, mounted only on a deliberate flip so they simply don't exist in prod until then. Three actions, each guarded:

  • Reset activity progress — a read-only preview (impact counts + a cert-revoke warning) then execute (snapshot → foreign-key-safe hard delete → reconcile completion and certification).
  • Reset a student's password — issues a one-time password via the auth provider.
  • Remove a graded submission — surgical delete with an un-pass reconcile; platform/system admin only, managers excluded.
Guard
Each destructive call requires you to type the target's email back before it runs.
Scope
A company manager may run the two milder actions on their own people; only platform can remove a grade. Out-of-scope targets return 404, never 403.

The rules underneath

Guardrails that apply everywhere

Three conventions hold across the whole back-office, live or not.

Audit trail

Every console mutation, and both halves of a company's life (created and edited), write a row to platform_audit_log — who, what, when, from one place.

Deny = 404

Out-of-scope reads return 404, never 403, so the API never confirms that a record you're not allowed to see even exists.

Destructive = typed confirm

Reset, password-reset and remove-submission each make you type the target's email back before they run — no single-click irreversibles.

Who can do what

Three tiers, one boundary

System admin — Edge8

Everything the back office exposes, cross-company and unscoped. Very few accounts. This is the platform tier.

Platform operator — console

Reads plus the support inbox today; a separate allowlist, no user_role needed, every action audited. An extra lock within the platform tier.

Company manager

Their own company only — see Workflow 01. Can run the milder remediation actions on their own people; grade-removal stays with platform. The admin tier.

The canonical model

There are three tiers only — platform, admin, learner — resolved in one place (progress_authz.resolve_tier()). platform_operator is an extra console lock within platform, not a fourth tier.
