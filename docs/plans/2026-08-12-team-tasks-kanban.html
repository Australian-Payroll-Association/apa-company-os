Edge8 OS, build plan

Team Tasks Kanban

A team-level task board on Edge8 OS. One table, one board component, one central view and one view per department. Admin sees and manages everything, managers work their reports' lanes, team members work their own. Client roadmap items, work requests, and coaching commitments feed the board instead of living beside it. Tasks carry one level of subtasks for composite work, and the product team runs its stories in sprints on the same table.

Interpretation of "roadmap items need to be moved": a roadmap item is promoted onto the board as a linked task. The client_backlog_items row stays where it is (it is the client-facing record in the portal roadmap); the task carries a foreign key back to it. Nothing is duplicated and nothing disappears from the client's view. If you meant physically migrating roadmap rows into the tasks table instead, flag it before the roadmap phase.
Coaching privacy boundary: the coaching module was built with two-tier visibility and its migration states the commitments ledger holds "commitments, never tasks". This plan keeps that invariant: the ledger stays the source of truth inside coaching, and a commitment reaches the open-book board only when its owner explicitly sends it there, with a board-facing title they control. Nothing from a 1-1 auto-publishes.

Task shapes by department

One table serves three shapes of work. Nothing below needs a different data model; the shape is just which optional columns are used.

  • Operations one-off: a single card with a due date. "Buy the replacement monitor by Aug 20." No sprint, no subtasks.
  • Operations composite: a parent task with subtasks, each independently owned and dated. "Run the Sydney retreat, Aug 31 to Sept 1" with subtasks: 1. survey the participants, 2. buy the Mac Mini, 3. book the plane. The parent is the card on the board (showing 2/3 done); the subtasks are the checklist inside it, and each appears in its assignee's "My tasks".
  • Product story: a task pulled into a sprint (sprint_id set). "This week we have ten stories." A story can also carry subtasks as its breakdown; rollover at sprint close moves the story and its open subtasks together.

An operations manager ensuring the team has the best equipment works the composite shape: one standing parent per initiative, subtasks per purchase, and the equipment register keeps custody once items arrive (that handoff stays manual in v1).

Data model

Two new tables following house conventions: company_os schema, RLS on with no policies, explicit service_role grant (without it the app cannot see the table), text statuses with CHECK, sort_order within a column, soft archive.

create table company_os.team_tasks (
  id               uuid primary key default gen_random_uuid(),
  team             text not null default 'operations'
                     check (team in ('operations','product')),
  title            text not null,
  description      text,
  status           text not null default 'todo'
                     check (status in ('backlog','todo','in_progress','review','done')),
  priority         text check (priority in ('low','normal','high','urgent')),
  assignee_id      uuid references company_os.people(id),
  created_by       uuid not null references company_os.people(id),
  due_date         date,
  sort_order       int not null default 0,

  -- subtasks: one level deep (enforced server-side), children die with the parent
  parent_task_id   uuid references company_os.team_tasks(id) on delete cascade,

  -- sprint container, used by product; null for un-sprinted work
  sprint_id        uuid references company_os.sprints(id) on delete set null,

  -- integration links: exactly one may be set, per source
  source           text not null default 'manual'
                     check (source in ('manual','roadmap','work_request','coaching')),
  backlog_item_id  uuid references company_os.client_backlog_items(id) on delete set null,
  work_request_id  uuid references company_os.work_requests(id) on delete set null,
  commitment_id    uuid references company_os.coaching_commitments(id) on delete set null,

  archived_at      timestamptz,
  archived_by      text,
  created_at       timestamptz not null default now(),
  updated_at       timestamptz not null default now()
);

create table company_os.sprints (
  id          uuid primary key default gen_random_uuid(),
  team        text not null default 'product'
                check (team in ('operations','product')),
  name        text not null,                    -- 'Sprint 12', 'Aug 17-28'
  goal        text,                             -- the one-line sprint goal
  starts_on   date not null,
  ends_on     date not null,
  status      text not null default 'planned'
                check (status in ('planned','active','closed')),
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  check (ends_on > starts_on)
);

-- one active sprint per team at a time
create unique index on company_os.sprints (team) where status = 'active';

create index on company_os.team_tasks (parent_task_id) where parent_task_id is not null;
create index on company_os.team_tasks (team, status, sort_order) where archived_at is null;
create index on company_os.team_tasks (assignee_id) where archived_at is null;
create index on company_os.team_tasks (sprint_id) where sprint_id is not null;
create index on company_os.team_tasks (backlog_item_id) where backlog_item_id is not null;
create index on company_os.team_tasks (commitment_id) where commitment_id is not null;

alter table company_os.team_tasks enable row level security;
alter table company_os.sprints enable row level security;
grant select, insert, update, delete on company_os.team_tasks to service_role;
grant select, insert, update, delete on company_os.sprints to service_role;

Why sprints live on the same table

The product team's sprint is a time-boxed container over the same work, not a different kind of work. Keeping it on team_tasks means the central board, the integrations, and the permission model all apply to sprint work for free, and a product task still shows up when leadership looks at the company-wide view. A dedicated tool only becomes worth it if the product team later needs estimation, velocity charts, or epic hierarchies; the sprint_id design leaves that door open without blocking it.

Conventions that apply

  • CHECK drift rule: any new team, status, or source value written by app code ships its constraint migration in the same PR, verified with a rolled-back probe insert.
  • Done is a column, deleted is an archive. done keeps the win visible on the board; archived_at clears it. No hard deletes.
  • Manager scope is derived, not stored. Manager relationships come from people.manager_id, resolved with an explicit query (never a PostgREST self-FK embed, which resolves reversed).
  • Identity: the team portal resolves the caller through the existing auth_user_id → people linkage. All access rules are enforced server-side in actions; the client only ever talks to the service-role server.
  • Coaching tables stay locked down. coaching_commitments already revokes chatbot roles; the board only ever reads the commitment via the server action that created the link, and the task row itself carries no 1-1 content beyond the title its owner chose.
  • Caching: all pages set fetchCache = 'force-no-store' (the Next 14 data-cache freeze that bit the ATS pages).

Views and permission matrix

There is no separate manager app. Admin lives at /admin/operations/tasks; managers and team members share /team/tasks, and the server decides their edit scope. One board component, rendered with two lenses:

  • Central board: the default view, all departments together, each card carrying a department chip. This is the leadership and cross-team lens.
  • Department boards: the same page filtered to one department (tabs: All / Operations / Product). Product's tab adds the sprint lens: a sprint selector (active sprint by default), the sprint goal in the header, and a backlog panel for un-sprinted product tasks.

Branches, loops, and backward moves

plan ↻ active ↻ closeThe whole workflow is a loop on the team's cadence (dates are free-form; two weeks is a convention, not a constraint).
mid-sprint addUrgent work can be pulled into the active sprint. The card gets a "added mid-sprint" marker so scope creep is visible at close, not hidden.
mid-sprint removeDescoped tasks drop back to the product backlog (sprint_id cleared), keeping their status and history.
rollover → next sprintUnfinished stories roll into the next sprint by default at close, each one individually confirmable. A story's open subtasks travel with it (W7).
rollover → backlogOr a task that keeps rolling over gets demoted to backlog instead: three sprints of rollover is a prioritisation signal, and the close screen shows the rollover count.
integrations respect sprintsRoadmap promotions (W3) and work requests (W4) targeting product land in the product backlog, never directly in the active sprint; pulling them in is a planning decision.

Deliberately out of v1

  • Comments on tasks. If needed, a task_comments table follows the coaching-goal-comments pattern later.
  • Nesting beyond one level, labels, estimates, velocity charts. Subtasks are in (one level, W7); sub-subtasks are not. If product later needs estimation and velocity, that is the trigger to revisit (the sprint_id design keeps the data ready for it).
  • Configurable columns. Statuses are fixed by CHECK, matching every other board in the app. A new column is a migration, not a settings screen.
  • Auto-publishing coaching content. Commitments reach the board one at a time, by their owner's hand, always.
  • Departments beyond Operations and Product. The schema is ready (team CHECK); these two prove the flow first.
  • Notifications. No Lark pings on assignment in v1; the open-book board is the notification.
Definition of done for the feature: Operations runs a real week on the board including one composite task worked through subtasks (the Sydney retreat shape); Product plans, runs, and closes one full sprint including a rollover; at least one client roadmap item, one work request, and one coaching commitment travel their full loop (including a backward move) without leaving the app.
