Team Tasks Kanban

A team-level task board on Edge8 OS. One table, one board component, three scoped views: admin sees and manages everything, managers work their reports' lanes, team members work their own. Client roadmap items and work requests feed the board instead of living beside it.

Data model

One new table following house conventions: company_os schema, RLS on with no policies, explicit service_role grant (without it the app cannot see the table), text statuses with CHECK, sort_order within a column, soft archive.

create table company_os.team_tasks (
  id               uuid primary key default gen_random_uuid(),
  team             text not null default 'operations'
                     check (team in ('operations')),
  title            text not null,
  description      text,
  status           text not null default 'todo'
                     check (status in ('backlog','todo','in_progress','review','done')),
  priority         text check (priority in ('low','normal','high','urgent')),
  assignee_id      uuid references company_os.people(id),
  created_by       uuid not null references company_os.people(id),
  due_date         date,
  sort_order       int not null default 0,

  -- integration links: exactly one may be set, per source
  source           text not null default 'manual'
                     check (source in ('manual','roadmap','work_request')),
  backlog_item_id  uuid references company_os.client_backlog_items(id) on delete set null,
  work_request_id  uuid references company_os.work_requests(id) on delete set null,

  archived_at      timestamptz,
  archived_by      text,
  created_at       timestamptz not null default now(),
  updated_at       timestamptz not null default now()
);

create index on company_os.team_tasks (team, status, sort_order) where archived_at is null;
create index on company_os.team_tasks (assignee_id) where archived_at is null;
create index on company_os.team_tasks (backlog_item_id) where backlog_item_id is not null;

alter table company_os.team_tasks enable row level security;
grant select, insert, update, delete on company_os.team_tasks to service_role;

Conventions that apply

  • CHECK drift rule: any new team, status, or source value written by app code ships its constraint migration in the same PR, verified with a rolled-back probe insert.
  • Done is a column, deleted is an archive. done keeps the win visible on the board; archived_at clears it. No hard deletes.
  • Manager scope is derived, not stored. Manager relationships come from people.manager_id, resolved with an explicit query (never a PostgREST self-FK embed, which resolves reversed).
  • Identity: the team portal resolves the caller through the existing auth_user_id → people linkage. All access rules are enforced server-side in actions; the client only ever talks to the service-role server.
  • Caching: both pages set fetchCache = 'force-no-store' (the Next 14 data-cache freeze that bit the ATS pages).

Branches, loops, and backward moves

item ↻ more tasksA big roadmap item is promoted in chunks: promote again at any time, each task carries the same backlog_item_id.
ship prompt → keep activeWhen the last open linked task hits done, admin chooses: mark the roadmap item shipped, or keep it active because more chunks are coming. Never automatic, because the roadmap status is client-visible.
task blocked ← roadmapA blocked task surfaces on the roadmap item's admin view (linked-tasks shelf), so client conversations start from the real state.
client reprioritises ↻ boardWhen the client changes client_priority in the portal, linked open tasks are flagged on the board for admin to re-order. The loop runs as many times as the client changes their mind.
item parked → tasks archivedIf the roadmap item is parked or archived, its open linked tasks are prompted for archive (admin confirms, no cascade delete).

Branches and backward moves

done → complete requestCompleting the task prompts completion of the linked request; billing (including auto QBO invoicing for client requests) proceeds exactly as it does today.

no task (opt-out)Small requests can be accepted without spawning a board task; the checkbox defaults on. Not every request needs a card.

Build phases

Four PRs, each independently shippable and verified before the next starts. Board mechanics are copied from the existing DealsBoard / ApplicationsBoard components, not hand-rolled; UI comes from /admin/patterns.

Verify: promote a real accepted item twice (two chunks), complete both, confirm the ship prompt fires once and the portal roadmap view is unchanged until admin confirms.
4
Work request integration (W4). Spawn-task checkbox on request acceptance, request chip on the task card, completion handshake (task done prompts request completion; request cancellation archives the task).
Verify: full round trip on a test contractor request: accept → task → done → request completed, and the cancel path archives the task. Billing figures untouched.

Deliberately out of v1

  • Comments on tasks. If needed, a task_comments table follows the coaching-goal-comments pattern later.
  • Subtasks, labels, estimates. Chunking happens by promoting a roadmap item more than once, not by nesting cards.
  • Configurable columns. Statuses are fixed by CHECK, matching every other board in the app. A new column is a migration, not a settings screen.
  • Coaching commitments on the board. They stay in the coaching module; revisit only if the team asks.
  • Additional teams. The schema is ready (team CHECK), Operations proves the flow first.
  • Notifications. No Lark pings on assignment in v1; the open-book board is the notification.
Definition of done for the feature: Operations runs a real week on the board; at least one client roadmap item and one work request travel their full loop (including a backward move) without leaving the app.
