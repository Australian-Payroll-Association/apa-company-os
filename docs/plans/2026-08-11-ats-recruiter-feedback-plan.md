# ATS recruiter feedback — development plan

**Date:** 2026-08-11 · **Owner:** Dave · **Status:** ready to build
**Source:** `FEEDBACK ON EGDE8 OS.pdf` (recruiter feedback on the Talent → Applications modal)
**Branch:** `ats-recruiter-feedback` (rebase onto latest `origin/main` before coding)

## Context

A recruiter gave four pieces of feedback on the application detail modal in Talent →
Applications. The common thread: the modal is too read-only and append-only for how
recruiters actually work. They want editable, structured fields instead of a growing pile of
immutable notes, plus a shareable profile URL, delete, and a way to correct the AI screen after
interviews. A fifth thread emerged in discussion: capture the human corrections as training
logs to tune the screening agent.

## Ground truth (verified 2026-08-11)

- The rich modal (`ApplicationManage.tsx`, 658 lines) and its schema are already on
  `origin/main`. The AI-screen columns and `candidate_profile` satellite are deployed live.
- **AI screen storage:** `company_os.applications.ai_summary` (jsonb: `overview`, `skills[]`,
  `english`, `salary_expectation`, `notice_period`) + `ai_rating`, `ai_screen_status`,
  `ai_screen_error`, `ai_screened_at`, `ai_model`. Generated by `lib/resume-screen.ts`
  `screenApplication()` using `claude-opus-4-8`, structured output. Read-only in the UI.
  Re-scan overwrites `ai_summary`. **The AI screen is NOT a note.**
- **Notes storage:** `company_os.interactions` (`kind='note'`, `subject_type='application'`,
  `subject_id=<application id>`, plus `person_id`). Append-only. No edit/delete action exists.
  Added via `addApplicationNote`, read via `getApplicationNotes` (both in
  `app/admin/(dashboard)/talent/applications/actions.ts`).
- **English / Salary / Notice** shown in the modal live inside `ai_summary` jsonb (AI-extracted,
  read-only). They are not columns.
- **Editable profile fields today:** `updateApplicantProfile(personId, patch)` splits writes:
  `people` ← `phone`, `linkedin_url`; `candidate_profile` (satellite, upsert on `person_id`) ←
  `headline`, `current_title`, `portfolio_url`, `do_not_hire`.
- **Application fields:** `updateApplication` writes `applications` (stage, status, rating,
  rejection_reason). Both actions call `recordAudit` + `revalidatePath`.
- **Deep link:** none. The modal is pure client state (`useState(selectedId)` in
  `ApplicationsTable.tsx`). Reloading loses it. No `?application=` handling.
- **Model:** application → person directly (`applications.person_id → people.id`), recruiting
  satellite `candidate_profile` keyed by `person_id`. `candidates` table is legacy/retired.

## Design principles

**Machine layer, human layer.** The AI screen stays a read-only, re-runnable machine artifact.
Humans never edit it in place (a re-scan would wipe edits, and we would lose the AI-vs-human
line). Instead, humans write to a parallel layer that overrides the AI values on display.

**Three distinct assessment layers, kept separate:**
1. **AI Screen** — machine, read-only. `applications.ai_*`.
2. **HR Assessment** — recruiter, one editable free-text field, overwritable. New column.
3. **Interview Results** — append-only thread, one dated + attributed entry per interviewer.
   The existing notes thread, relabeled.

## Decisions locked (from discussion)

- AI screen read-only; add a human layer that overrides it. (not: edit the AI in place)
- HR Assessment is a **distinct**, single free-text, autosaving field. (not: structured, not a note)
- Interview Results = renamed notes thread, **append-only per interviewer**, author + date shown.
- Delete = **soft-archive** the application (reversible, audited). Button labeled "Delete" with undo.
- Unique URL = **full-page applicant profile** at `/admin/talent/applications/<id>`, which
  **replaces** the drawer. Fetched by id server-side, so it resolves for closed/filled reqs.
- English / Salary / Notice = **editable, per-person** on `candidate_profile`; recruiter value
  overrides the AI-extracted value with a subtle "from AI screen" hint on fallback.
- Salary expectation = **structured** amount + currency (follow existing `*_cents` convention,
  default VND).
- Capture human corrections as **training logs** to tune the screening agent.

## Migration (one file, `company_os`)

```
-- applications
ALTER TABLE company_os.applications ADD COLUMN hr_assessment text;
ALTER TABLE company_os.applications ADD COLUMN archived_at timestamptz;

-- candidate_profile (per-person, editable overrides)
ALTER TABLE company_os.candidate_profile ADD COLUMN english_proficiency text;
ALTER TABLE company_os.candidate_profile ADD COLUMN salary_expectation_cents bigint;
ALTER TABLE company_os.candidate_profile ADD COLUMN salary_expectation_currency text;
ALTER TABLE company_os.candidate_profile ADD COLUMN notice_period text;

-- training log (append-only correction events)
CREATE TABLE company_os.ai_screen_corrections (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  application_id uuid NOT NULL REFERENCES company_os.applications(id),
  person_id      uuid REFERENCES company_os.people(id),
  ai_model       text,
  field          text NOT NULL,          -- english | salary | notice | rating | other
  ai_value       text,                   -- the AI value at correction time (snapshot)
  human_value    text,                   -- what the recruiter set it to
  corrected_by   uuid,                   -- admin auth user / person id
  created_at     timestamptz NOT NULL DEFAULT now()
);
```

All new columns + table get explicit `service_role` grants (company_os grants rule), and the
`ai_screen_corrections` table is excluded from the NL→SQL assistant surface (it is operational,
not a data-answer surface). Migration ships in the same PR as the code.

## Workstreams

### 1. HR Assessment (distinct, editable)
- New `applications.hr_assessment` column.
- `updateApplication` (or a dedicated `updateHrAssessment`) writes it; autosave on blur like the
  other fields. Audited.
- UI: its own labeled section in the profile, visually separate from the AI Screen block and the
  Interview Results thread. Placeholder makes ownership clear ("Recruiter assessment, editable").

### 2. Editable per-person fields with AI-override precedence
- New `candidate_profile` columns: `english_proficiency`, `salary_expectation_cents` +
  `_currency`, `notice_period`.
- Extend `updateApplicantProfile` to write them.
- Display precedence: show the recruiter value if set; else show the AI-extracted value from
  `ai_summary` with a muted "from AI screen" tag. Editing promotes it to the human value.
- Re-scan never overwrites a human-entered value (it writes `ai_summary` only; display reads the
  human column first).
- Salary input: amount + currency selector, stored in minor units; default VND.

### 3. Interview Results (renamed append-only thread)
- Relabel the Notes section to "Interview Results" (UI copy only; storage unchanged).
- Each entry renders **author + date** (resolve `interactions.owner_id` → person name). Confirm
  `addApplicationNote` records the acting admin as author; add if missing.
- Stays append-only. Readability fix = layout (author, date, spacing, newest first), not editing.

### 4. Full-page applicant profile + delete
- New route `app/admin/(dashboard)/talent/applications/[id]/page.tsx` — server component that
  fetches the application by id (joins person + candidate_profile + ai fields + notes),
  regardless of req status. Renders the same sections as the modal, full width.
- Refactor `ApplicationManage.tsx` sections so they are shared between the (now removed) drawer
  and the page. `ApplicationsTable.tsx` rows become links to `/admin/talent/applications/<id>`.
  Remove the `DetailDrawer` usage for applications.
- **Delete** button on the page → `archiveApplication(id)` sets `archived_at`, audited, redirects
  to the list with an undo toast/link (`unarchiveApplication`). List filters out
  `archived_at is not null` by default; an "Archived" filter chip surfaces them for restore.

### 5. AI training / eval loop
- **Prediction log:** already captured on the application (`ai_summary`, `ai_rating`, `ai_model`,
  `ai_screened_at`).
- **Correction events:** when `updateApplicantProfile` changes a field that the AI had populated
  (english/salary/notice) or a recruiter overrides the rating, write one row to
  `ai_screen_corrections` capturing the AI value at that moment (drift-proof; survives re-scan).
- **Outcome labels:** derivable from `applications.status` / stage / `rating` /
  `candidate_profile.do_not_hire` (did the AI's score track the real decision).
- **Export:** an admin action that emits JSONL joining resume ref + AI output + corrections +
  outcome, filterable by `ai_model`, for feeding prompt/eval tuning. v1 can be a
  download button on an admin screening/settings page; the SQL view backs it.
- **Future (noted, not v1):** an append-only `ai_screen_runs` table to version every screen run
  for model-vs-model comparison.

## Sequencing

Single PR unless Dave prefers phasing. Suggested build order:
1. Migration (columns + table + grants).
2. Server actions: extend `updateApplicantProfile` + `updateApplication`; add
   `archiveApplication` / `unarchiveApplication`; add correction-event capture; author on notes.
3. Full-page profile route + shared sections; remove drawer; list rows → links.
4. UI: HR Assessment field, editable English/Salary/Notice with AI fallback, Interview Results

5. Training export (action + view + button).

## Verification (no dev server)

Per project rule, verify with `npx tsc --noEmit` and `next build`, not a running server. Manual
DB smoke: probe insert into `ai_screen_corrections`; confirm precedence display with a screened
row that has an override; confirm archived rows drop from the list and restore.

## Risks / edge cases

- **Re-scan vs human values:** guaranteed safe because re-scan writes `ai_summary` only and
  display reads human columns first. Correction events snapshot the AI value, so the training
  pair survives.
- **Closed-req deep links:** the page fetches by id directly, bypassing the open-req list filter.
- **Author on old notes:** historical `interactions` without `owner_id` render "Unknown"; only new
  entries carry the author. Acceptable.
- **Salary currency:** VND has no minor unit in practice; store major units × 100 as cents for
  convention consistency, format without decimals for VND.
- **Delete semantics:** archive is reversible by design. If true purge is needed for confirmed
  duplicates, add an admin-only hard delete later behind a confirm; out of v1 scope.

## Open questions

- Training export delivery: a download button on an admin screening page (recommended) vs a
  scheduled snapshot to storage. Default to the button for v1.
- Should HR Assessment or field overrides ever feed back into the stack-rank / AI fit score?
  Default: no for v1 (keep the AI score machine-pure; humans rank via stars + status).
